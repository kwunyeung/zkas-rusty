# Browser payment signer

`zkas-browser-signer` wraps the SDK version-3 multi-output payment signer for a wallet-controlled browser context. Its constructor takes the wallet's existing 32-byte Orchard account seed, the selected network and genesis, and an immutable payment intent approved in the wallet UI. The caller must keep this constructor and its input buffer inside the wallet's private context. The binding clears the supplied `Uint8Array` on both successful and failed construction and zeroizes its retained seed when freed. It exposes the public account address and per-action spend authorization signatures; it does not export the seed, viewing key, arbitrary-message signatures, or a generic signing method.

The binding does not derive a mnemonic or alter account numbering. A wallet must supply the same account seed it already derives for each account. The fixed test fixture uses the public BIP-39 test phrase `abandon` repeated eleven times followed by `about`, an empty passphrase, coin type 111111, and ZIP-32 account indices 0 and 1. Account 0 maps to seed `20468ca002014b860fce6926a03c8eeaceebb48b365160f60836cc3a111d3b38` and address `zkas:px8dx79gspafw49lw989mzdxhlqt6pehw9ql54r8ayyymv59vday3mtyxm432g4t6we2gygp3udqluy`; account 1 maps to seed `fa502dd864b61baccb7eb86cd30d2eeef6a39ab32ef09b415054ea8a2c157c32` and address `zkas:p8vmwuwk2npzsjc4udm4zurtdpd76rwyqwma3j9fdda3lc4yhsp30tcesf54ehq29t66jysxg9mc25s`. These are public test-only values.

The approved intent JSON has exactly `account`, `outputs`, and `maxFeeSompi`. Each output has exactly `recipient`, `amountSompi`, and `memoHex`. Amounts and the fee ceiling are canonical unsigned decimal strings; addresses must use the selected network's canonical encoding; memo hex must be lowercase and encode exactly 512 bytes. The constructor checks the signer account, output count, unique recipients, positive amounts, and supported arithmetic bounds. A wallet should bind the approval to its own origin, account, and network selection before calling this private constructor. It must never accept an app-supplied approval object as an independent source of authority.

`sign_prepared_v3` accepts the bounded SDK `PreparedPaymentMultiEnvelope` JSON, validates its version/checksum/canonical encoding, and calls `SoftwareSigner::verify_and_sign_multi` against the retained account, genesis, and approved intent. The SDK checks normal-payment context, actual bundle shape and fee, output recovery, and every real spend's randomized action key before returning signatures. One handle retains its first successfully signed envelope and exact signatures: repeating that envelope returns identical signatures, while a different envelope requires a new wallet approval and handle.

Immediately after signing and before finalization, a wallet may call `export_signed_v3_ticket` and store its result **encrypted in wallet-private storage**. The ticket contains the canonical prepared V3 envelope, the original complete action-signature map, and a digest of the exact local approval, network address, and genesis; it contains no seed or viewing key. It must never be sent to an application or stored in an application-readable journal. After restart, the wallet reconstructs a new private handle from its locally derived account seed, selected network/genesis, and the same immutable locally approved intent, then calls `import_signed_v3_ticket`. Import rejects malformed, oversized, noncanonical, duplicate-field, partial, or unknown-field tickets. It rechecks the exact approval digest and all prepared-payment policy, derives each real action key from the wallet seed and disclosed randomizer, and verifies each retained signature against that action's original signature message without signing again. An imported handle accepts only that prepared envelope; its finalized transaction check still requires the exact imported signatures and pins the first verified full bytes. The wallet must retain the encrypted ticket with its immutable approval and payment journal until authoritative reconciliation permits release. The wallet journal owns the logical payment identity and replay exclusion; the ticket is recovery material, not a new approval or a broadcast instruction.

After the daemon finalizes the payment, `verify_finalized_v3` accepts only its complete lowercase-hex Borsh transaction bytes. It checks the bounded normal shielded-payment shape and actual mass, recomputes the transaction ID and SHA-256, compares every unsigned effect and spend signature to the exact envelope and signatures retained by this handle, and verifies the completed Orchard proof, spend authorizations, and binding signature. The response contains the exact verified transaction hex, transaction ID, and SHA-256. The first verified bytes are retained for identical retries; later different bytes are refused. This binding does not create a proof, submit, or broadcast a transaction. The wallet must keep the handle private and use the verified bytes and identifiers in its credentialed submit flow.

From `sdk/browser-signer`, build with:

```sh
CARGO_TARGET_DIR=/tmp/zkas-browser-signer-target wasm-pack build --target web --release --out-dir /tmp/zkas-browser-signer-wasm --out-name zkas_browser_signer --mode no-install -- --offline --locked
```

This uses the crate's wasm32-only `getrandom` 0.4 `wasm_js` backend and target cfg. The release profile disables `wasm-opt`: the available older optimizer rejects bulk-memory instructions in current Rust output, while the browser and Node WASM engines accept them. Do not commit the generated package; pin and audit its bytes when integrating into a wallet. The dependency lock pins `wasm-bindgen` 0.2.100. The verified build used Rust/Cargo 1.97.1, `wasm-pack` 0.13.0, and Node 26.9.0.

For the native and actual JavaScript/WASM fixture checks, run from the workspace root:

```sh
cargo test --offline --locked -p zkas-browser-signer
node sdk/browser-signer/tests/browser-v3.mjs /tmp/zkas-browser-signer-wasm /tmp/zkas-browser-v3-signatures.json
cargo run --offline --locked --quiet -p zkas-browser-signer --example verify_v3_signatures /tmp/zkas-browser-v3-signatures.json
```

The prepared fixture was generated by `cargo run --offline --locked -p zkas-browser-signer --example generate_v3_fixture`. A second public dummy fixture contains a complete proved transaction built from a synthetic note and Merkle path. Spend authorization signatures may vary between runs, so the browser test creates a private handle, signs that fixture's prepared envelope, and uses the `finalize_v3_fixture` native example to insert those exact signatures into the proved bundle before invoking `verify_finalized_v3`. Fresh signed handles exercise corrupted proof, spend authorization, binding signature, effects, Borsh shape, cached transaction ID, mass and trailing-byte failures. Native tests compare the bounded browser transaction decoder with the consensus transaction ID and mass calculations on all supported networks. Generated WASM and JavaScript must be hashed and audited before wallet integration; no generated package is committed here.
