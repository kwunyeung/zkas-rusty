# Bounded shielded history transport

`GET /api/chain/shielded-history?after=<64 lowercase hex>&limit=<1..32>` reads one selected shielded-chain page from the daemon's configured node. It uses a separate fixed-node gRPC connection, capped at 8 MiB decoded per response. The normal wallet request and sync connections retain their existing limits. A configured global bearer token and the daemon's explicit CORS allow-list apply to this route unchanged. There is no wallet token, viewing key, account, URL, or request body in this API.

The JSON response is version 1. All chain `u64` values, including DAA, blue score, timestamp, coinbase value, and source generation, are decimal **strings**. Hashes, coinbase scripts and complete compact accepted-action bytes are lowercase hex. `acceptedTxids` and `acceptedCompactHex` are parallel arrays in the node's selected acceptance order. Each compact action is 148 bytes; an accepted transaction can contain several actions. `tipBefore` and `tipAfter` are separate observations, and the latter may have advanced during the read.

The source generation starts from a fresh process-random value and advances on each separate history-channel connection. It is an observation fence, not a durable chain identifier. A client must revalidate the selected history after any generation change or restart.

The history channel has a single cleanup owner. A failed or canceled page read requests retirement of that connection generation; the owner removes its published handle and completes gRPC disconnect before opening another history channel. Stopping the HTTP server also requests retirement. Shutdown waits up to five seconds for ordinary cleanup, but that is a soft wait: an unusually slow disconnect continues under its owner. The process keeps at most two history supervisor tasks: one can own the active or retiring channel, and one can wait for its single process permit. A third overlapping server invocation starts no history worker and remains unavailable for that invocation, even if earlier cleanup later finishes; a subsequent invocation can retry. An incomplete or failed disconnect never authorizes a replacement connection. The regular wallet request and sync channels are separate.

`source.configuredGenesis` comes from daemon network parameters; it is **not** an independently observed node genesis hash. `source.observedNetwork` is checked against the exact configured network ID at both ends of the read, and both sync checks must be true. `floor` reports the checkpoint and history-retention flags actually returned by the node. `floor.historyComplete` describes the node's retained shielded index history; it does not assert availability of full transaction bodies or that this page completes a wallet scan.

The shielded-block RPC has no page-level protocol-support flag. `page.protocolEvidence` is `id-bearing-actions-observed` only when this page actually contains accepted compact actions paired with nonempty transaction IDs. It is `unknown` for an empty or actionless page. Actions without parallel IDs make the entire page unavailable. `page.reorged=true` is the node's explicit selected-cursor result and has no blocks. Missing history, source changes, an unsupported response, inconsistent fields, exceeded transport limits or a deadline produce an error, never a shortened successful page.

One request allows at most 32 blocks, 512 accepted transactions, 512 actions per transaction, 2,000,000 compact bytes, 2,048 coinbase outputs, 128 script bytes per output, 6 MiB complete JSON, two simultaneous handlers, and ten node calls. The page-read operation has a 20-second timeout, followed by elapsed-time checks around response construction. That timer is not a hard total HTTP deadline: request framing, initial slot locking, serialization work, and channel cleanup are not preempted by it. These are transport bounds, not consensus maxima. Smaller `limit` values can recover a valid page that exceeds a transport bound. The response is a trusted configured-node observation, not a cryptographic inclusion proof, funding authorization, wallet receipt, or complete-history claim. A wallet must separately establish a selected genesis-backed prefix, reconcile reorgs and gaps, and verify any transaction body it uses.
